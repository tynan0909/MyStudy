6. AOP

SpringFramework에는
DI와
AOP가 있는데

DI는 의존성 주입이고 프레임워크에서 역으로 나에게 주입을 해준다
주입을 하려면 스프링이 내 클래스를 빈으로 알고잇어야 함
빈을 관리하는 컨테이너를 빈 컨테이너라고 함. 이걸 설정하는게 스프링프레임워크의 시작

jsp내장객체 쓰는것처럼 .찍어서 쓰면 댄다
아무리 많은 객체가 있어도 스프링이 커버가능
하지만 첫 로딩에 시간이 걸린다(스태틱처럼 미리 올리는거라)

반면 AOP란?
Aspect-Oriented Programming(관점지향프로그래밍)의 약자

보안
로깅
트랜잭션
결제
등을 통제할 수 있음

OOP와 비교하자면
OOP는 추상적이고 
얘는 실무적?

프록시: A와 B, C라는 기능군은 오브젝트로 뭉쳐있는데,
3가지가 서로 공통적인 핵심부분이 있으면 커팅해서(가져와서) 
원래의 기능을 감싸는 것(프록시)를 만든다.

이거로 보안, 로깅, 트랜잭션등등 할 수 있음.

이러면 JIT(just in time)컴파일러 할 수 잇음
코딩을 일일히 추가할 필요 없이 코드를 만들어 놓고 클래스는 놔둘수 잇음

a,b,c,d 메소드가 있는데 이게 실행될때 마다 카톡을 보내고싶으면
원래는 전부 이걸 시작할때 카톡보내기 메소드를 넣어야함

하지만 AOP에서는 abcdefg...원하는 메소드를 골라만 놓고(커팅) 이벤트 등록(카톡발송클래스)을 하면 된다
이걸 할수 잇는 이유가 프록시(프락치)

즉 DI는 개발자가 개발에만 집중시킬수 잇게 만든거고
AOP는 개복수술하지 않고 간단하게 패치하는거임

스프링은 클래스명에 service가 들어가면 트랜잭션되게 해놧음
그래서 이름을 통일성 잇게 해야 써먹기 좋다고 함

전처리 3가지인 filter intercept aop를 구분하여 설명하시오
filter는		맨앞에서 방화벽
intercept는		컨트롤러에 대한걸 사전에 차단(특정한uri로,컨트롤러 앞에서)
aop는		특정한 비지니스 로직이 돌아갈때(업무에서,service앞에서)

우리는 aop의 커팅지점과 어드바이스만 준비하면 알아서 프락치를 이용해 만든다잉

public class AServiceProxy implements AService{
	private AService a;
	private Kakao k;
	
	public void aProxy() {
		k.send();
		a.a();
	}

	@Override
	public void a() {
		this.aProxy();
	}
}

이렇게 해놓으면 원본은 건들지 않고 메소드 넣을 수 있음

JDK dynamic proxies는 인터페이스스타일 CGLIB는 상속스타일


결국 스프링 aop(프록시)의 용도를 쉽게 설명하면
원본소스를 건들지 않고 메소드를 달아줄 수 잇어서
대수술을 하지 않아도 된다는거임

@Aspect(AOP하겟다)랑 @Component(bean으로 인식)를 달아주고
@Before("커팅지점") 설정해주면 댐

그후 @Around하고 조인포인트 설정해줌



7. TASK

task(작업)란?
job schedule
online: 실시간처리 	ex)내가 식당에서 계산함
batch: 묶음처리 		ex)카드사가 밤에 한번에 묶어서 계산한거 처리

일정시간이 되면 처리한다
스케줄
1. Linux에서	Cron이라는 기술이 잇음	-> 1시10분에 ~~해줘~
2. DB 오라클에서 프로시져도 스케줄관리임	-> 1시에 ~~해줘~
3. Java에서 		Task로도 스케줄관리		-> 이건 프로그램상에서

큰작업은 Spring Batch
작은작업은 Spring Task

지하철현황판처럼 ㅁ->ㅁ->ㅁ->ㅁ->ㅁ ㅁ이 메소드고 ->가 진행방향이면
어디서 에러가 나는지 표시할 수 있게?

리눅스 크론 검색해보면 나오긴함
분 시간 일 월 요일
*	*  *	*    * 별숫자로 카테고리 정하고 숫자넣으면댐
10 ***은 10일마다 돌려라
좀더 자세히 조건넣을수 잇긴한데 여백이 부족하므로 적지않겟다

만약 컴퓨터가 바빠서 스케줄이 되어도 안돌아갈수 잇어서
중요한건 os에서 돌리게 해야함


@Scheduled(cron = "0 0 2 * * *")이거 메소드위에 적어주면

CORS는 **Cross-Origin Resource Sharing (교차 출처 리소스 공유)**의 약자로,
웹 브라우저가 **다른 출처(Origin)**의 서버로부터 리소스(데이터)를 
안전하게 요청할 수 있도록 허용하는 보안 메커니즘입니다.

@CrossOrigin(어쩌고..) 서버의 응답 헤더에 CORS 정책 관련 정보를 자동으로 추가하도록 스프링에게 지시합니다.
